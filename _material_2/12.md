# 12. Käännöksen analyysi

{: .code-title }
collatz.c
```c
#include <stdio.h>

long collatz(long n) {
    long steps = 1;
    while (n != 1) {
        steps++;
        if (n % 2 == 0) {
            n = n / 2;
        } else {
            n = 3 * n + 1;
        }
    }
    return steps;
}

int main(void) {
    int t;
    scanf("%d", &t);
    long total = 0;
    for (int i = 1; i <= t; i++) {
        total += collatz(i);
    }
    printf("%ld\n", total);
}
```

## Käännös ilman optimointia

Tarkastellaan ensin ohjelman käännöstä, jossa `gcc`-komennossa ei ole annettu ohjeeksi optimoida koodia. Seuraavassa on käännetyn ohjelman assembly-koodi tässä tilanteessa:

{: .code-title }
collatz.s
```nasm
    .text
collatz:
    endbr64
    push rbp
    mov rbp, rsp
    mov [rbp-24], rdi
    mov [rbp-8], 1
    jmp .L2
.L5:
    add [rbp-8], 1
    mov rax, [rbp-24]
    and eax, 1
    test rax, rax
    jne .L3
    mov rax, [rbp-24]
    mov rdx, rax
    shr rdx, 63
    add rax, rdx
    sar rax
    mov [rbp-24], rax
    jmp .L2
.L3:
    mov rdx, [rbp-24]
    mov rax, rdx
    add rax, rax
    add rax, rdx
    add rax, 1
    mov [rbp-24], rax
.L2:
    cmp [rbp-24], 1
    jne .L5
    mov rax, [rbp-8]
    pop rbp
    ret
    .section .rodata
.LC0:
    .string "%d"
.LC1:
    .string "%ld\n"
    .text
main:
    endbr64
    push rbp
    mov rbp, rsp
    sub rsp, 32
    mov rax, [fs:40]
    mov [rbp-8], rax
    xor eax, eax
    lea rax, [rbp-24]
    mov rsi, rax
    lea rax, .LC0[rip]
    mov rdi, rax
    mov eax, 0
    call __isoc99_scanf@PLT
    mov [rbp-16], 0
    mov [rbp-20], 1
    jmp .L8
.L9:
    mov eax, [rbp-20]
    cdqe
    mov rdi, rax
    call collatz
    add [rbp-16], rax
    add [rbp-20], 1
.L8:
    mov eax, [rbp-24]
    cmp [rbp-20], eax
    jle .L9
    mov rax, [rbp-16]
    mov rsi, rax
    lea rax, .LC1[rip]
    mov rdi, rax
    mov eax, 0
    call printf@PLT
    mov eax, 0
    mov rdx, [rbp-8]
    sub rdx, [fs:40]
    je .L11
    call __stack_chk_fail@PLT
.L11:
    leave
    ret
```

Koodi muodostuu kahdesta aliohjelmasta `collatz` ja `main`, jotka vastaavat melko suoraan alkuperäisen C-koodin funktioita. Aliohjelmat varaavat pinosta muistia C-koodia vastaaville muuttujille, tekevät laskutoimituksia rekisterien avulla ja käyttävät hyppykomentoja ehtojen ja silmukoiden toteuttamiseen.

### Koodin tietoturva

Komento `endbr64` aliohjelmien alussa liittyy tietoturvaan. Komento määrittelee, että kyseinen kohta koodissa on aliohjelman alku, jonne on sallittua hypätä muualta koodista epäsuoran osoituksen kautta. TODO: tarkemmin

Toinen tietoturvaan liittyvä asia on pinoon laitettava _kanarialintu_:

```nasm
    mov rax, [fs:40]
    mov [rbp-8], rax
```

Kanarialintu on salainen arvo, joka lisätään pinoon ennen paikallista muistinvarausta. Ideana on, että jos koodissa on pinon sisältöön kohdistuva puskuriylivuoto, se menee kanarialinnun päälle. Aliohjelma tarkastaa lopussa seuraavasti, ettei kanarialintu ole muuttunut:

```nasm
    mov rdx, [rbp-8]
    sub rdx, [fs:40]
    je .L11
    call __stack_chk_fail@PLT
```

Jos kanarialintu on muuttunut, kutsutaan aliohjelmaa `__stack_chk_fail`, joka käytännössä lopettaa ohjelman suorituksen välittömästi.

### Pinon käsittely

Molemmat aliohjelmat sisältävät paikallisia muuttujia, jotka on tallennettu pinoon. Tavallisen käytännön mukaisesti aliohjelmat lisäävät alussa rekisterin `rbp` sisällön pinoon ja palauttavat sen lopuksi pinosta. Aliohjelmat eroavat kuitenkin siinä, miten ne käsittelevät rekisteriä `rsp`.

Aliohjelma `main` varaa pinosta 16 tavua tilaa komennolla `sub rsp, 16`, joka siirtää rekisterin `rsp` pinon päälle. Lopuksi aliohjelma kutsuu komentoa `leave`, joka palauttaa rekisterit `rsp` ja `rbp` ennalleen. Komento `leave` vastaa käytännössä seuraavia komentoja:

```nasm
    mov rsp, rbp
    pop rbp
```

<div class="note" markdown="1">
Komennon `leave` lisäksi x86-konekielessä on myös komento `enter`. Ideana on, että komento `enter` voidaan suorittaa aliohjelman alussa ja komento `leave` voidaan suorittaa aliohjelman lopussa.

Komento `enter` hoitaa rekisterin `rbp` alkukäsittelyn sekä varaa muistia pinosta paikallisille muuttujille. Komennolle annetaan varattavan muistin määrä sekä toisena parametrina aliohjelman taso, jota ei yleensä käytetä. Esimerkiksi seuraavat koodit tarkoittavat samaa:

```nasm
    enter 16, 0
```

```nasm
    push rbp
    mov rbp, rsp
    sub rsp, 16
```

Komentoa `enter` ei kuitenkaan nykyään yleensä käytetä, koska prosessorit suorittavat komennon hitaasti ja on tehokkaampaa kutsua erillisiä komentoja yllä olevalla tavalla. Komento `leave` sen sijaan on tehokas ja käyttökelpoinen.
</div>

Aliohjelma `collatz` _ei_ päivitä rekisteriä `rsp` osoittamaan pinon päälle, vaikka se säilyttää pinossa paikallisia muuttujia. Näin voi tehdä, koska pinon päällä on 128 tavun kokoinen _punainen alue_ (_red zone_), jossa olevaa muistia aliohjelman on sallittua käyttää muuttamatta rekisteriä `rsp`. Tämä tehostaa koodia, koska koodissa ei tarvita komentoja rekisterin `rsp` käsittelyyn.

Punaista aluetta voi käyttää, kun aliohjelma ei kutsu muita aliohjelmia eikä haittaa, vaikka rekisteri `rsp` ei osoita pinon päälle. Tämän takia punaista aluetta voi käyttää aliohjelmassa `collatz`, mutta sitä ei voi käyttää aliohjelmassa `main`.

### Parillisuustarkastus

Seuraava koodi vastaa parillisuustarkastusta `n % 2 == 0`:

```nasm
    and eax, 1
    test rax, rax
    jne .L3
```

Koodi tutkii rekisterissä `rax` olevan luvun parillisuuden ja hyppää nimiöön `.L3` luvun ollessa pariton. Koodin toiminta perustuu siihen, että luku on parillinen tarkalleen silloin, kun sen viimeinen bitti on 0.

Ensin koodi suorittaa and-operaation, jonka seurauksena rekisterin `rax` sisältö on joko 0 (parillinen) tai 1 (pariton). Tämän jälkeen koodissa on komento `test`, joka muistuttaa aiemmin käsiteltyä komentoa `cmp`. Komento `test` suorittaa and-operaation ja päivittää lippurekisteriä tämän komennon tuloksen mukaisesti.

Koska rekisterin `rax` sisältö on joko 0 tai 1, komennon `test` tulos on sama kuin rekisterin `rax` sisältö ja komento `jne` suorittaa hypyn sisällön ollessa 1 eli alkuperäisen luvun ollessa pariton.

### Kahdella jakaminen

Seuraava koodi vastaa lauseketta `n = n / 2`:

```nasm
    mov rdx, rax
    shr rdx, 63
    add rax, rdx
    sar rax
```

Tässä rekisteri `rax` sisältää jaettavan luvun. Koodi suorittaa bittisiirron oikealle komennolla `sar`, mikä on tehokas tapa jakaa luku kahdella. Tätä ennen koodissa on kuitenkin monimutkaisuutta sen takia, että koodi ottaa huomioon tilanteen, jossa jaettava luku on negatiivinen.

C-kielessä jakolaskun `n / 2` tulos vastaa komentoa `sar` positiivisilla luvuilla, mutta negatiivisilla luvuilla tulos voi erota. Esimerkiksi C-kielen lausekkeen `-5 / 2` arvo on `-2`, koska jakolaskun tulos pyöristyy nollan suuntaan. Komento `sar` antaisi kuitenkin tässä tilanteessa tuloksen `-3`. Tämän takia koodi varautuu seuraavasti tilanteeseen, jossa jaettavana on negatiivinen pariton luku:

- Koodi laittaa ensin bittisiirron avulla rekisterin `rdx` sisällöksi rekisterin `rax` luvun etumerkin (0 = positiivinen, 1 = negatiivinen). Koodi siirtää bittejä 63 askelta oikealle, koska luvussa on 64 bittiä.

- Tämän jälkeen koodi lisää rekisterissä `rdx` olevan etumerkin rekisterin `rax` arvoon eli käytännössä säilyttää rekisterin `rax` arvon entisellään, jos arvo on positiivinen, ja kasvattaa rekisterin arvoa yhdellä, jos arvo on negatiivinen.

- Lopuksi koodi suorittaa aritmeettisen bittisiirron (`sar`), joka jakaa luvun kahdella ja antaa nyt C-kielen toimintaa vastaavan tuloksen myös negatiiviselle parittomalle luvulle.

<div class="note" markdown="1">
Vaikka Collatzin lukujonon luvut ovat positiivisia, negatiivinen luku on tässä mahdollinen sen takia, että suurella alkuarvolla lukujonon luku saattaa olla niin suuri, ettei se mahdu 64-bittiseen muuttujaan, ja luvusta tulee negatiivinen ylivuodon seurauksena.

Koodin taustaoletuksena on, ettei näin käy, ja koodi toimisi tässä tapauksessa selkeästi väärin. Kääntäjä kuitenkin kääntää konekielisen koodin toimimaan C-koodia vastaavasti myös tässä tilanteessa.

Tässä tapauksessa on kuitenkin oikeastaan tarpeetonta varautua negatiiviseen parittomaan lukuun, koska jako kahdella tehdään vain siinä tapauksessa, että luku on parillinen. Tässä kääntäjä ei ole hyödyntänyt tietoa siitä, että edeltävä koodi on varmistanut luvun olevan parillinen.
</div>

### Kertolasku ja kasvatus

Seuraava koodi vastaa lauseketta `n = 3 * n + 1`:

```nasm
    mov rax, rdx
    add rax, rax
    add rax, rdx
    add rax, 1
```

Tässä rekisteri `rax` sisältää käsiteltävän luvun. Koodin toiminta vastaa lauseketta `n + n + n + 1`, jossa kertolasku on korvattu yhteenlaskulla. Tämä on tässä tilanteessa järkevää, koska yhteenlasku on kertolaskua yksinkertaisempi operaatio.

<div class="note" markdown="1">
Miksi koodi käyttää komentoa `add` muuttujan arvon kasvattamiseen yhdellä, vaikka konekielessä olisi myös tähän räätälöity komento `inc`?

Kääntäjät toimivat usein näin, koska komennot `add` ja `inc` eroavat sisäisesti siinä, miten ne päivittävät prosessorin lippurekisteriä. Komento `inc` päivittää lippurekisterin vain osittain, minkä takia komennon suorituksen rinnakkaistaminen on vaikeampaa kuin komennossa `add`. TODO: paremmin
</div>

## Käännös optimoinnin kanssa

Tarkastellaan sitten saman koodin optimoitua versiota, jonka käännöksessä `gcc`-komennossa on annettu lippu `-O2`:

{: .code-title }
collatz.s
```nasm
    .text
collatz:
    endbr64
    mov eax, 1
    cmp rdi, 1
    je .L1
.L5:
    add rax, 1
    test dil, 1
    jne .L3
    mov rdx, rdi
    shr rdx, 63
    add rdi, rdx
    sar rdi
    cmp rdi, 1
    jne .L5
.L1:
    ret
.L3:
    lea rdi, [rdi+rdi*2+1]
    add rax, 1
    test dil, 1
    jne .L3
    mov rdx, rdi
    shr rdx, 63
    add rdi, rdx
    sar rdi
    jmp .L5
    .section .rodata
.LC0:
    .string "%d"
.LC1:
    .string "%ld\n"
    .section .text
main:
    endbr64
    sub rsp, 24
    lea rdi, .LC0[rip]
    mov rax, [fs:40]
    mov [rsp+8], rax
    xor eax, eax
    lea rsi, [rsp+4]
    call __isoc99_scanf@PLT
    mov eax, [rsp+4]
    test eax, eax
    jle .L18
    lea r8d, [rax+1]
    mov ecx, 1
    xor edi, edi
    jmp .L16
.L24:
    mov rsi, rax
    shr rsi, 63
    add rax, rsi
    sar rax
    cmp rax, 1
    jne .L15
.L12:
    add rcx, 1
    add rdi, rdx
    cmp r8, rcx
    je .L11
.L16:
    mov rax, rcx
    mov edx, 1
    cmp rcx, 1
    je .L12
.L15:
    add rdx, 1
    test al, 1
    je .L24
.L13:
    lea rax, [rax+rax*2+1]
    add rdx, 1
    test al, 1
    jne .L13
    mov rsi, rax
    shr rsi, 63
    add rax, rsi
    sar rax
    jmp .L15
.L18:
    xor edi, edi
.L11:
    mov rdx, rdi
    xor eax, eax
    lea rsi, .LC1[rip]
    mov edi, 2
    call __printf_chk@PLT
    mov rax, [rsp+8]
    sub rax, [fs:40]
    jne .L25
    xor eax, eax
    add rsp, 24
    ret
.L25:
    call __stack_chk_fail@PLT
```

Tämä koodi eroaa melko paljon alkuperäisestä koodista, ja koodin seuraaminen on vaikeampaa. Aliohjelmat säilyttävät tietoa enimmäkseen rekistereissä pinon sijasta, mikä on tehokkaampaa. Aliohjelma `main` käyttää myös pinoa, mutta se ei käytä rekisteriä `rbp` vaan viittaa pinoon suoraan rekisterin `rsp` kautta.

Koodia tutkiessa voi aluksi hämmentää, että koodi määrittelee aliohjelman `collatz` mutta ei kutsu sitä, vaan aliohjelma `main` sisältää upotettuna aliohjelman `collatz` logiikan. Tämän selittää, että koodi toimii tehokkaammin ilman aliohjelmakutsuja, mutta toisaalta aliohjelma `collatz` tulee kuitenkin olla olemassa, koska sitä voitaisiin kutsua itsenäisenä käännösyksikön ulkopuolelta.

### Optimoitu laskutoimitus

Collatz-jonon laskemista on optimoitu koodissa seuraavasti:

```nasm
.L3:
    lea rdi, [rdi+rdi*2+1]
    add rax, 1
    test dil, 1
    jne .L3
    mov rdx, rdi
    shr rdx, 63
    add rdi, rdx
    sar rdi
```

Tässä operaatio `n = 3 * n + 1` on toteutettu `lea`-trikillä, jolloin sen pystyy laskemaan yksittäisellä komennolla. Tämä operaatio on silmukassa, jota toistetaan niin kauan kuin luku säilyy parittomana. Tämän jälkeen luku on parillinen, jolloin koodi jakaa sen kahdella samalla tavalla kuin aiemmassa versiossa.

Tästä näkee, että optimoinnista huolimatta koodi laskee edelleen melko kömpelösti lausekkeen `n / 2`. Myös yllä oleva silmukka on kyseenalainen, koska `n`:n ollessa pariton luku lausekkeen `3 * n + 1` arvo on varmasti parillinen. Niinpä silmukkaa ei pitäisi koskaan suorittaa useita kertoja peräkkäin.

Voimme helpottaa kääntäjän elämää tekemällä pienen muutoksen C-koodiin: muutetaan funktiota `collatz` niin, että parametrin `n` tyyppi on `unsigned long` eikä `long`. Tämän ansiosta kääntäjä tietää, ettei `n` voi sisältää negatiivista lukua, minkä pitäisi tehostaa ainakin jakolaskua.

Tämän muutoksen seurauksena käännös muuttuu näin:

```nasm
.L22:
    shr rax
.L15:
    cmp rax, 1
    je .L13
.L16:
    add rdx, 1
    test al, 1
    je .L22
    lea rax, [rax+rax*2+1]
    jmp .L15
```

Tästä näkee, että muutos tuotti toivotun tuloksen, koska nyt koodi toteuttaa jakolaskun yksittäisellä komennolla `shr`. Tämä on esimerkki siitä, miten konekielisen koodin tutkiminen voi auttaa löytämään koodia hidastavan tekijän. Seuraava taulukko näyttää koodin eri käännösten suoritusajat testikoneella:

Koodin versio | Käännöstapa | Suoritusaika
--- | ---
Alkuperäinen | Ei optimointia | 9.4 s
Alkuperäinen | Optimointi | 4.7 s
Muutettu `long` -> `unsigned long` | Optimointi | 4.1 s

## ELF-tiedosto

```c
#include <stdio.h>
#include <ctype.h>

struct ELFHeader {
    char ident[16];
    short type;
    short machine;
    int version;
    long entry;
    long phoff;
    long shoff;
    int flags;
    short ehsize;
    short phentsize;
    short phnum;
    short shentsize;
    short shnum;
    short shstrndx;
};

struct PHTEntry {
    int type;
    int flags;
    long offset;
    long vaddr;
    long paddr;
    long filesz;
    long memsz;
    long align;
};

int main(int argc, char **argv) {
    if (argc != 2) {
        printf("Wrong number of parameters\n");
        return 1;
    }
    FILE *file = fopen(argv[1], "rb");
    if (file == NULL) {
        printf("Can't open the file");
        return 1;
    }
    struct ELFHeader elf_header;
    fread(&elf_header, sizeof(elf_header), 1, file);

    if (*((int*)elf_header.ident) == 0x464c457f) {
        printf("ELF signature found\n");
    } else {
        printf("Incorrect file format\n");
        return 1;
    }

    if (elf_header.ident[4] != 2 || elf_header.machine != 0x3e) {
        printf("Only x86-64 format supported\n");
        return 1;
    }

    printf("Program entry offset: %06lx\n", elf_header.entry);

    unsigned char buffer[16];
    int pht_count = 0;

    for (int i = 0; i < elf_header.phnum; i++) {
        int offset = elf_header.phoff + i * elf_header.phentsize;
        fseek(file, offset, SEEK_SET);
        struct PHTEntry pht_entry;
        fread(&pht_entry, sizeof(pht_entry), 1, file);

        if (pht_entry.type != 1) continue;

        pht_count++;
        printf("\nPHT load entry #%d\n", pht_count);
        fseek(file, pht_entry.offset, SEEK_SET);

        printf("Flags: ");
        if (pht_entry.flags & 1) printf("exec ");
        if (pht_entry.flags & 2) printf("write ");
        if (pht_entry.flags & 4) printf("read ");
        printf("\n");

        printf("File offset: %06lx\n", pht_entry.offset);
        printf("Memory address: %06lx\n", pht_entry.vaddr);

        int total = pht_entry.filesz;
        while (total) {
            int count = total < 16 ? total : 16;
            fread(&buffer, 1, count, file);
            for (int i = 0; i < count; i++) {
                printf("%02x ", buffer[i]);
            }
            for (int i = 3 * count; i < 50; i++) {
                printf(" ");
            }
            for (int i = 0; i < count; i++) {
                char symbol = isprint(buffer[i]) ? buffer[i] : '.';
                printf("%c", symbol);
            }
            printf("\n");
            total -= count;
        }
    }

    fclose(file);
}
```
